# SEO/AEO audit — skills.sshlg.me, 2026-08-26

**Scope.** The 12 URLs `sitemap.xml` declares, across 4 template families
(`/`, `/agents/`, `/routing/`, `/skills/{slug}/` ×9). Observed 2026-08-26,
`seo-aeo-audit@0.25.1`.

**What could not be checked, and why.** Named rather than left to be inferred:

| Instrument | State | Consequence |
|---|---|---|
| Search Console | no credential in this harness | declared-vs-indexed per template is unknown; no position, coverage or query data |
| Bing / Yandex webmaster | no credential | no second engine's view of the same pages |
| Analytics · server logs | not available | no crawl-rate, no landing-page behaviour, no orphan detection from traffic |
| Crawl export | none run | **orphans, click depth and internal-link counts are unknown** — a sitemap carries no link graph and these were not inferred from path shape |
| JS-rendered markup | n/a | the site ships no client-side rendering, so the static read is the whole page |

Everything below is measured on this date or it is not here.

## Track A — access · `PASS`

`robots.txt` allows all and names the sitemap; every declared URL resolves 200;
the old `ssheleg.github.io/sshlg-skills` origin 301s to this one. No blockers.

## Track B — canonicalization · `PASS`

Every page's `<link rel=canonical>` equals the URL it is served at, checked by
`test/site_test.js` on every build rather than by inspection.

## Track C — architecture · one finding, fixed

| observation | value | date |
|---|---|---|
| `/agents/` repeated the entire 9-card pack grid that `/` already carries | 9 duplicate card blocks, 378 words of link text | 2026-08-26 |

The page's job is one table; the trailing grid duplicated the front page's own
section and diluted it. Replaced with a chip row and one link to the front page's
descriptions.

## Track F — extractability / AEO · two findings

**F1 · read budget.** The share of the first ~5700 characters that is content
rather than link markers. The window is one engine's median (ChatGPT Deep
Research), so the share is the finding and the window is not a budget every engine
enforces — tier `FIELD`.

| page | before | after | severity before |
|---|---|---|---|
| `/agents/` | 54.5% content | **78.4%** | high |
| `/` | 47.9% content | 47.9% — **not addressed**, see the plan | high |
| `/skills/telegram-dev/` | 62.4% | — | none |
| `/routing/` | 78.4% | — | none |

**F2 · the answers had no questions.** `/agents/` existed to answer one recurring
question and answered it in a table, so the Q→A pair an engine needs had to be
reconstructed. Five questions the page actually gets asked are now on the page as
visible text, and an `FAQPage` node is built **from the same array the page
renders**, so the two cannot drift.

## Track G — entity consensus · one finding, fixed

| template | JSON-LD before | author entity |
|---|---|---|
| `/` | WebSite, ItemList | ✓ |
| `/skills/{slug}/` | SoftwareApplication, BreadcrumbList | ✓ |
| `/agents/` | BreadcrumbList | **✗** |

Two of four templates carried no entity at all — including the page most likely to

## Tracks D, E, H, I, J · not run, and why

`D intent` and `J measurement` need query data this harness has no credential for.
`E content value` and `I risk` were out of scope for a pass targeted at what the
brief called *"what is still missing"*. `H experience` is partially covered by the
build gate (no external hosts, inline CSS, one request) but Core Web Vitals were
not measured — no field data available.

`K agent surface` was not run: the site sells nothing an agent could buy or call.

## An instrument disagreement, recorded rather than resolved

`page_audit.py` reports `faq-schema-partial` at `medium`/`CONFIRMED` — *"1 of 5
declared answers are not in the served body text."* Under the rule the script
documents (first 60 characters, whitespace-collapsed, lowercased, against the
served text) **all five match**, reproduced directly against the built file. The
page is 32 KB, so truncation is not the cause.

The property that matters was verified independently and holds: **every marked-up
question and answer appears verbatim in the served body.** The disagreement lives
inside the parser's own text stream and could not be reproduced from outside, so
it is reported as an instrument note, not as a site finding — and the page was not
mutated further to satisfy it.

## Addendum — found by the post-deploy check, same day

**Two `Person` nodes on one page, with nothing linking them.** `CONFIRMED`,
observed by fetching the deployed `/` at commit `8ab7f9b`: the layout emits the
full publisher, and `WebSite.author` and `SoftwareApplication.author` each emitted
their own `{"@type":"Person","name":"Sergey Sheleg","sameAs":["…x.com/sshlg93"]}`.
Two candidate entities a consumer has to guess are the same — which is the defect
this very pass was about, shipped by the pass itself.

Fixed at the same layer as the original: one `@id` (`https://skills.sshlg.me/#person`)
on the publisher, and every other reference is `{"@id": …}` describing nothing.

**The instrument note that matters more than the finding.** The first post-deploy
check reported `Person:0` on all four pages and I nearly recorded that. The pattern
was `"@type": "Person"` with a space; the served JSON is minified. **The grep was
wrong, not the site.** Two consequences, both written down rather than remembered:

- `test/site_test.js` had **no JSON-LD check at all** — 30 checks over a site whose
  structured data was its subject, and none of them parsed it. Two now do, and both
  were watched failing against planted defects (re-describe the person: 1 failure;
  drop the `@id`: 2).
- A check that greps rendered HTML for a formatted substring is testing the
  formatter. The new fixtures `JSON.parse` the blocks and walk the objects.

This also re-opens the earlier `faq-schema-partial` disagreement as **less certain
than recorded**: an instrument that disagreed with a hand-check was resolved in the
site's favour once today, and the reason was my pattern. It stays recorded as a
disagreement, now with a live example of that class resolving the other way.

## Addendum 2 — what the repaired probe then found

Each fix made the next thing visible, which is worth recording as the shape of the
pass rather than three separate findings:

| Probe said | Was it the site? | What it actually was |
|---|---|---|
| entity missing on all 4 pages | no | the grep pattern had a space; served JSON is minified |
| `refs=0` on all 5 pages | no | the walker keyed on `@type`; a reference has none |
| `refs=0` on `/agents/`, `/routing/` | **yes** | those pages attached the entity to nothing |

The third is the real finding, `CONFIRMED`: a `FAQPage` and a `BreadcrumbList` with
an unreferenced `Person` beside them. A breadcrumb states position, not authorship,
so on the two pages likeliest to be quoted every content node was anonymous.
`/routing/` now has a `WebPage` node, and the `FAQPage` and front-page `ItemList`
name their author by `@id`.

The fixture's `refsSeen > 0` was counted site-wide, so a single page with a
reference satisfied it for thirteen. Per page now — and that change found a
fourteenth page, `404.html`, which is now `noindex` and exempt by that declared
signal rather than by its filename.

**What this says about the instrument list at the top of this audit.** Two of the
three rows above are instrument defects that a less careful reading would have
recorded as site findings, and the first one nearly was. That is the same class as
the `faq-schema-partial` disagreement recorded earlier — which is why it stays
recorded as a disagreement and not as a site defect.

### Correction to addendum 2 — the 404 case is measured, not precautionary

The `noindex` was reasoned about as a hedge against "a host that serves the body
with 200". Measured after deploy, that host is this one:

```
GET https://skills.sshlg.me/404.html      -> 200
GET https://skills.sshlg.me/no-such-page/ -> 404
```

GitHub Pages serves the file with **200 at its own address** and uses it as the
body for a real 404 elsewhere. So a page reading *"That page is not here"* was
fetchable, indexable and carrying the site's own name and author metadata. It is
out of `sitemap.xml` (0 references), which is why nothing had pointed a crawler at
it — an omission, not a control. The `noindex` is the control.
