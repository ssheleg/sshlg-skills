# SEO/AEO audit — the whole family surface, 2026-08-27

**Scope.** Wider than the 2026-08-26 pass, which audited the site alone. Three surfaces:
the 12 URLs `sitemap.xml` declares, the **10 GitHub repositories** (umbrella + 9
members), and the **10 npm package pages**. Observed 2026-08-27, `seo-aeo-audit@0.25.5`
from the submodule at `skills/seo-aeo-audit` (v0.25.3 pinned; the script reports its own
package version).

**The headline is one line.** The site went live 2026-08-25 and **Google has never
crawled it** — 12 of 12 URLs report `URL is unknown to Google`, because the sitemap had
never been submitted to any Search Console property. Everything the previous pass fixed
was invisible. That is fixed below, and it changes what the rest of this audit is *for*:
until 2026-08-27 there was nothing to optimise against, only something to prepare.

## What could not be checked, and why

| Instrument | State | Consequence |
|---|---|---|
| Search Console | **reachable** — `sc-domain:sshlg.me`, 22 properties visible | the previous audit recorded "no credential"; the real gate was a **quota project**, and the domain property covers the subdomain. See the correction below |
| PageSpeed Insights | HTTP 429, quota exhausted | no field Core Web Vitals; Track H rests on the build gate alone |
| Bing / Yandex webmaster | no credential | no second engine's view |
| Analytics · server logs | none | no crawl-rate or landing behaviour for the site |
| Crawl export | none run | site orphans and click depth not measured from a link graph |
| GitHub's own ranking model | not public | Track C for the repositories is measured by *observed rank*, never by inferred cause |

**Correction to the 2026-08-26 audit.** That pass listed Search Console as
`no credential in this harness` and its plan closed by asking the next audit to open by
measuring declared-vs-indexed. Both the instrument row and the plan were wrong about the
cause: the credential existed. Two things stood between it and the data — the API needs a
`x-goog-user-project` header naming a project the account can use, and the property is
registered as `sc-domain:sshlg.me`, a **domain property**, which covers `skills.sshlg.me`
without a per-subdomain entry. An instrument reported as absent that was merely
mis-addressed is the same class as the three instrument defects that pass recorded, and it
is the fourth.

## Track A — access · one BLOCKER, fixed today

| observation | value | date |
|---|---|---|
| URL Inspection over all 12 sitemap URLs | **12 of 12** `verdict=NEUTRAL`, `coverage=URL is unknown to Google`, `last crawl: None` | 2026-08-27 |
| sitemaps submitted to `sc-domain:sshlg.me` | **none** | 2026-08-27, before the fix |
| first Pages deployment | 2026-08-25T09:01:53Z (`gh run list --workflow=pages.yml`) | 2026-08-27 |

`robots.txt` allows all and names the sitemap; every URL resolves 200; the old
`ssheleg.github.io/sshlg-skills` origin 301s. Access was never the problem —
**announcement** was. A sitemap named in `robots.txt` and submitted nowhere relies on a
crawler finding the origin on its own, and for a two-day-old subdomain with almost no
inbound links that had not happened.

**Fixed 2026-08-27T00:34:43Z.** Submitted via the Search Console API; the property now
reports `path=https://skills.sshlg.me/sitemap.xml · errors=0 · warnings=0 ·
contents: web submitted=12`.

**What this does NOT prove.** Submission is not indexation. The `indexed` field on the
sitemaps endpoint reads 0 and Google no longer populates it, so it is not a measurement —
the skill's own probe says so. The honest statement is that the site is now *declared*;
whether it is crawled is a question only a re-inspection in some days can answer, and the
plan's single next action is to ask it.

**Zero impressions is not a finding.** `gsc_pull` over 90 days returns 23 impressions
for `https://sshlg.me/` and no row for any `skills.sshlg.me` URL. Against a site that
first deployed 48 hours earlier and had never been crawled, that is the expected
observation, not evidence of a defect. It is recorded so the next pass has a baseline.

## Track F — extractability / AEO · the leak this pass closed

`page_audit.py` over all 12 URLs: 5 × `read-budget` (high), 1 × `low-extractable-text`
(medium), 1 × `faq-schema-partial` (medium, the instrument disagreement carried over).

The previous pass measured four pages and found `/` at 47.9%. Measuring all twelve shows
**four pack pages are worse than the front page**, and the driver is not the front page's
card grid that pass deferred as G2 — it is shared chrome plus thin bodies. Prose share,
link text excluded, measured on the served HTML 2026-08-27:

| page | prose words | link words | prose share |
|---|---|---|---|
| `/skills/seo-aeo-audit/` | 173 | 318 | **35.2%** |
| `/skills/make-skill/` | 353 | 330 | 51.7% |
| `/skills/agent-sync/` | 349 | 315 | 52.6% |
| `/skills/sheleg-dev/` | 475 | 336 | 58.6% |
| `/skills/task-pipeline/` | 763 | 320 | 70.5% |
| `/routing/` | 2771 | 43 | 98.5% |

Link chrome is **near-constant at 315–336 words on every pack page** — the header, the
breadcrumb and the footer — so the variance is entirely in how much each page says. The
page most likely to be reached by "what does seo-aeo-audit do" was 65% navigation.

**Root cause, and it is not a content trade-off.** Each pack page rendered the *names* of
the skills it ships as pills and never said what any of them **does**. The answer was
already written, in the one place that cannot drift from what the skill actually
advertises: the `description` in each skill's own `SKILL.md` front matter, which is the
string the agent runtime itself matches on. 21 skills carry 3,330 words of it and the site
rendered none.

**Fixed.** `scripts/site.js#skillBrief` derives one capability paragraph per shipped
skill. Prose share after, same measurement, same day:

| page | before | after |
|---|---|---|
| `/skills/sheleg-dev/` | 58.6% | **76.1%** |
| `/skills/agent-stack/` | 63.2% | **75.4%** |
| `/skills/super-ux/` | 66.1% | **75.3%** |
| `/skills/telegram-dev/` | 64.4% | **73.8%** |
| `/skills/seo-aeo-audit/` | 35.2% | **41.8%** |

`seo-aeo-audit` remains the thinnest because it is a one-skill pack with genuinely less
to say; it improved by 6.6 points and is not forced further, because padding a page to
clear a threshold is the myth this skill's own reference list refuses.

**What was deliberately NOT published.** Those descriptions end in a bilingual list of
the phrases that trigger the skill — `"SEO audit" / "сделай SEO-аудит"`, eleven more per
skill. Rendered on a public page that is a keyword list wearing prose. `lib/brief.js`
removes it and keeps the two halves a reader and an engine both want: what the skill is
for, and what it is not for. Shipping the raw string would have been the one tactic
non-negotiable #5 forbids, in an audit of this family's own site.

**The defect this pass shipped and caught before deploy.** The first stripper used a
character class of every quote mark, so `"why doesn't ChatGPT cite us"` ended at `doesn`
and half a Russian keyword list bled into `/skills/seo-aeo-audit/` as prose. It was caught
by asserting the *shape* of every rendered brief rather than by reading them —
`test/brief_test.js`, 8 fixtures, watched failing against two planted defects. Same class
as the three instrument defects recorded on 2026-08-26: the transform was wrong, and only
a check that ran over what actually ships would say so.

## Track C — architecture, on GitHub · measured, not inferred

The repositories are **not findable for the terms that matter**. `search/repositories`,
best-match, top 100, 2026-08-27:

| query | best family rank |
|---|---|
| `agent skills` | **absent from top 100** |
| `claude code plugin` | **absent from top 100** |
| `claude code skills` | **absent from top 100** |
| `seo aeo audit` | 43 (`ssheleg/seo-aeo-audit`) |
| `telegram mini apps skill` | 17 (`ssheleg/telegram-dev`) |

It ranks only where the query nearly spells the repository name. **Cause is not
metadata**, and this is the finding that matters: all ten repositories already carry a
description, a homepage pointing at the site, 8 topics each and a custom Open Graph image
— checked on all ten. The comparison that settles it is `mattpocock/skills`: **237,955
stars, 20,248 forks, zero topics, no custom OG image** (verified against the API and
cross-checked; for scale, `freeCodeCamp` is 454,640). Tier `STUDY` — GitHub's ranking
model is not public, so the *correlation* is what is observed here and the mechanism is
not claimed. What is `CONFIRMED` is the negative: metadata completeness is not sufficient,
because the counter-example is maximally complete on our side and absent on his.

## Track G — entity consensus · one open leak

The hub is stated inconsistently across the surfaces that point at it:

| surface | points at | count |
|---|---|---|
| GitHub repo `homepageUrl` | `skills.sshlg.me/...` | **10 of 10** ✓ |
| npm `homepage` | `github.com/ssheleg/...` | 9 of 10 |
| npm `homepage` | `skills.sshlg.me/skills/telegram-dev/` | 1 of 10 (`@ssheleg/telegram-dev`) |

Nine packages route a reader to GitHub and GitHub routes them to the site, so the site is
reached in two hops from npm and one from GitHub, and one package disagrees with its eight
siblings. Not a blocker — every path arrives — but the canonical hub should be asserted
identically by every surface that asserts it. Tier `CONFIRMED` for the inconsistency;
`HYPOTHESIS` for any ranking effect, since npm's outbound links are `nofollow` and the
gain is entity consensus rather than equity. Not fixed in this pass: it changes 9
`package.json` files and only takes effect on publish, so it belongs to the next release
rather than to nine releases cut for one field.

## Track A′ — a discovery channel that already sends traffic, with the front door missing

`skills.sh` lists agent-skill repositories and installs from them. Measured 2026-08-27:

| repository | `skills.sh/<repo>` | badge install count |
|---|---|---|
| the 9 members | **200**, all nine | 12 – 699 each, **2,051 total** |
| `ssheleg/sshlg-skills` (umbrella) | **404** | badge renders `resource not found` |

The umbrella — the one repository whose job is installing the whole family — is the only
one missing. The cause is structural: it holds its nine packs as **git submodules**, so a
fresh clone contains no `SKILL.md` anywhere and an indexer that looks for skills finds
none. This is not hypothetical traffic: `traffic/popular/referrers` already shows
`skills.sh` referring to the family, alongside `podmanifesto.org` (29), `github.com` (33)
and `Google` (10).

## Track J — measurement · the instrument that did not exist

There was no way to answer "how much traffic does the family get". GitHub reports per
repository and the family is ten of them, and **the traffic API keeps 14 days and nothing
older**, so any month not captured is unrecoverable. Built in this pass:
`scripts/traffic.js` folds all ten into one figure and `--snapshot` merges daily rows into
`docs/evidence/traffic.ndjson` keyed by repo and date. First reading, 2026-08-27, trailing
14 days:

| | views | unique | clones | unique |
|---|---|---|---|---|
| **family, 10 repos** | **182** | 97 | **19,733** | 3,453 |

The shape is the finding: **108 clones per page view.** Clones are dominated by
`npx skills add`, which clones the repository — so the family is being *installed* far
more than its GitHub pages are *read*, and the read side is what search and answer engines
see. Summed uniques are not people (one reader of three packs counts three times) and the
report says so in its own output.
