2. Что аудировалось и чем

Что это за продукт. Не хостируемый сервис, а дистрибутив: zero-dependency Node-лаунчер плюс восемь скилов как пинованные git-сабмодули, которые ставятся в 12 не-Claude агентов через skills CLI плюс плагин Claude Code, на машине пользователя. Отсюда два следствия для аудита. Первое: «прод» здесь — это npm-реестр, GitHub-релизы и CI, а не веб-сервер. Второе: Sentry, APM и крэш-репортинга нет и быть не может в текущей архитектуре — код исполняется на машине пользователя, наружу не звонит. Это проверено, а не предположено (см. §5).

Высоко ③ Истёкшая лиза, которую невозможно подмести: идентичность рана — литерал "shared"

этот чекаут · воспроизводится чтением двух файлов

$ cat .agent-sync/leases/RELEASE-ALL.lock
{"run": "r-6e62c4dab", "ts": "2026-08-22T08:00:19Z", "ttl": 2700, ...}
# истекла 27,0 часов назад (ttl 45 минут)

$ cat .agent-sync/run-id
{"runs": {"shared": {"run": "r-6e62c4dab", "seen": "2026-08-23T11:44:17Z"}}}

Идентичность рана в этом чекауте хранится под ключом "shared" — то есть любая сессия здесь отвечает на тот же id. Поэтому классификатор не может доказать владение и честно докладывает [ambiguous] its run id matches, but this run's identity is the shared fallback — any other session in this checkout answers to the same id, so the match proves nothing, и оставляет файл. Результат: истёкшая лиза не подметается никогда, и остаток накапливается в репозитории, чья функция — координация.

Хук agent-sync докладывает это на каждом старте сессии. Доклад корректен; чего нет — пути, который его закрывает без ручного вмешательства.

Средне ④ hooks status никогда не бывает чистым — и это чистый ложный положительный

lib/hooks.js:130 · доказано вызовом plan() на живых настройках

$ node bin/sshlg-skills.js hooks status | tail -2
hooks: НЕ установлено или устарело — SessionStart (refreshed), UserPromptSubmit (refreshed),
  PreToolUse (refreshed), PostToolUse (refreshed)

При этом все девять файлов хуков байт-в-байт идентичны установленной копии (cmp -s для каждого → same), и все матчеры совпадают с WIRED. Причина — в plan():

const merged = others.concat([want[event]]);          // lib/hooks.js:130
if (JSON.stringify(existing) !== JSON.stringify(merged)) { … }

Запись семьи всегда переносится в конец массива. В settings.json она сейчас стоит первой — ровно на тех четырёх событиях, где рядом зарегистрирован чужой хук. Сравнение строк расходится только по порядку:

$ node -e '…plan(cur, root, {})…'
changed: ["SessionStart (refreshed)","UserPromptSubmit (refreshed)",
          "PreToolUse (refreshed)","PostToolUse (refreshed)"]
SessionStart identical: false
     SessionStart identical AFTER sorting: true      ← содержимое совпадает
PostToolUse  identical: false
     PostToolUse  identical AFTER sorting: true
Notification identical: true                          ← нет чужого хука → чисто

Два следствия, и второе хуже первого. Отчёт, который не может стать чистым, учит оператора его игнорировать — это тот самый провал, про который написано в CLAUDE.md этого репозитория («отказ без следующего шага — это то, как оператор учится выключать хук»). А hooks install, выполненный по этому докладу, переставит PreToolUse-гард семьи после чужого хука — для гарда, который отказывает, порядок не косметика.

Почему тест не поймал. test/hooks_test.js:43 утверждает идемпотентность по длине массива ('ours was appended twice'), а не по равенству плана. Дважды применённый план не растит массив — и проходит.
