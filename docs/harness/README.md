# The ssheleg harness

The ssheleg harness gives coding agents a working method: choose the right tools, preserve the intent of a task, verify the result and leave enough context for another run to continue. The skill family is its instruction and verification layer. Project Observatory is its separately installed observation tool.

The host agent still executes the model, tools and permission checks. Installing this harness does not create a sandbox, guarantee that an agent follows every instruction, or turn a local inspection into proof that production is safe.

## What each layer owns

| Layer | What it answers | Implemented by |
|---|---|---|
| Routing | Which capability owns this request, and where does it stop? | [Router registry](../../lib/routers-registry.js), [toolkit](../../lib/toolkit.js) |
| Delivery | What was requested, what depends on what, and what proves completion? | [task-pipeline](../../skills/task-pipeline/README.md) |
| Coordination | Who owns this work and this shared file? | [agent-sync](../../skills/agent-sync/README.md) |
| Specialist work | How should this interface, integration, design or agent system be built? | [Pinned skill packs](../../skills.json) |
| Learning | Which failure becomes a regression, and which instruction should retire? | [Retrospective contract](../../skills/task-pipeline/plugins/task-pipeline/skills/task-pipeline/references/retrospective.md) |
| Observation | What changed across explicitly enrolled projects and where are credential exposures? | Project Observatory, a separate portable distribution |

## A task through the harness

1. Inventory the tools available to the current agent. Select only the capabilities that serve the request.
2. Record the task's scope, dependencies, acceptance evidence and resume point in the repository.
3. For user-facing work, write scenarios before the interface. Keep product intent, wording and appearance connected.
4. Execute bounded work. Preserve unknowns and permission boundaries when a tool or integration is unavailable.
5. Verify the artifact that will ship. An eval result names its inputs, candidate revision and observed result; an unrun check stays unrun.
6. Leave a durable handoff with completed work, remaining work, evidence and one exact next action.
7. Use Observatory, when installed, to inspect project state after the task. Observation does not silently authorize changes to credentials or production.

## Installation boundaries

```sh
npx sshlg-skills install
npx --yes sshlg-skills@latest list
```

These commands install and inspect the skill family. Observatory has its own installation, data directory and permissions; it is not installed as a side effect. Existing pack names, package identifiers and standalone installations remain supported.

The launcher owns its marked routing blocks and managed installation mechanisms. Host-specific hooks and native plugins have different capabilities. A prompt-level rule is not a host-enforced permission boundary. Read the [agent compatibility page](https://skills.sshlg.me/agents/) before depending on a host-specific mechanism.

## What we take from ECC

The comparison uses a pinned ECC source snapshot rather than its popularity or advertised breadth. The adoption focuses on explicit installation ownership, bounded hook contracts, portable session handoff and artifact-bound evaluation evidence. The existing family contracts remain the single homes for those mechanisms. We do not import ECC's entire instruction stack or install its hooks alongside our routers.

The source analysis and implementation live in [agent-stack](https://github.com/ssheleg/agent-stack), which owns harness engineering. Research is provenance, not a runtime dependency.

## Observatory publication boundary

The public portable edition is prepared from generic source with a new Git history. Operational registries, local databases, credential material, private project documents and original repository history are excluded. Its documentation distinguishes portable capabilities from adapters still awaiting migration. Marketing examples must be synthetic or supported by a separately reviewed aggregate; a finding in a local transcript is not automatically a vulnerability in the tool that stored it.

## Verification and ownership

The family website is generated by [scripts/site.js](../../scripts/site.js) from [skills.json](../../skills.json); [test/site_test.js](../../test/site_test.js) checks page, link and version contracts. `npm test` runs the repository gate. Each member retains its own validator and release process.

The delivery plan is [2026-09-21-harness-observatory.md](../evidence/plans/2026-09-21-harness-observatory.md). Evidence of publication is recorded there and in its linked handoff, never inferred from a completed local build.
